#  Architecture Decisions

This document explains the key technology choices made while designing **Page Pulse**. Each decision was evaluated against possible alternatives based on performance, scalability, operational complexity, and suitability for the project requirements.

---

# Technology Decision Matrix

| Component          | Selected Technology       | Rejected Alternative   | Justification                                                                                                                                                                                                                                                                                          |
| ------------------ | ------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Caching Layer**  | **Upstash Redis**         | Memcached              | Upstash Redis provides a serverless, HTTP REST-based API with built-in persistence. It integrates easily with cloud deployments and allows configurable TTL-based caching without managing Redis infrastructure.                                                                                       |
| **Task Queue**     | **BullMQ (Redis-backed)** | RabbitMQ               | BullMQ leverages the existing Redis infrastructure, reducing deployment complexity while providing reliable background job processing. It can efficiently handle high-concurrency workloads (e.g., 500 concurrent audit requests) without introducing an additional messaging service.                 |
| **Parsing Engine** | **Cheerio + Axios**       | Puppeteer / Playwright | Axios efficiently fetches HTML content, while Cheerio parses HTML in memory with very low CPU and memory usage. Headless browsers such as Puppeteer and Playwright consume significantly more resources because they render an entire browser, making them unnecessary for simple metadata extraction. |

# Design Rationale

## 1. Caching Layer – Upstash Redis

### Why Upstash Redis?

The application frequently receives repeated audit requests for the same URLs. Instead of performing the same network request multiple times, audit results are cached in Redis.

### Benefits

* Fast response time for repeated requests.
* Configurable cache expiration using TTL.
* Persistent storage.
* Serverless architecture with no infrastructure management.
* REST API support suitable for cloud deployments.

# 2. Task Queue – BullMQ

### Why BullMQ?

Although the current version performs audits synchronously, BullMQ was selected as the preferred queue technology for future scalability.

For large traffic spikes or long-running audits, requests can be queued and processed asynchronously.

### Benefits

* Built on Redis (no extra infrastructure).
* Reliable job retries.
* Delayed and scheduled jobs.
* Background processing.
* High throughput for concurrent workloads.
* Easy integration with the existing Redis instance.

### Why Not RabbitMQ?

RabbitMQ is a powerful message broker but introduces additional deployment, monitoring, and maintenance overhead. Since Redis is already part of the architecture, BullMQ offers a simpler and more efficient solution.

---

# 3. Parsing Engine – Axios + Cheerio

### Why Axios?

Axios provides a simple, reliable HTTP client for downloading webpage HTML while supporting request timeouts and error handling.

### Why Cheerio?

Cheerio parses raw HTML without launching a browser, making it ideal for extracting metadata such as:

* Page title
* Meta description
* H1 tag
* Content length
* Content type

### Benefits

* Extremely fast parsing.
* Low memory consumption.
* Low CPU usage.
* Suitable for high-concurrency environments.
* Simple jQuery-like API.

### Why Not Puppeteer or Playwright?

Headless browsers render JavaScript and simulate a full browser environment. While useful for JavaScript-heavy websites, they consume considerably more RAM and CPU.

For Page Pulse, only HTML metadata extraction is required, making Cheerio the more efficient and scalable choice.

# Conclusion

The selected technologies prioritize **performance, simplicity, scalability, and maintainability**.

* **Upstash Redis** minimizes repeated network requests through fast, persistent caching.
* **BullMQ** provides a scalable path for background processing while reusing the existing Redis infrastructure.
* **Axios + Cheerio** deliver lightweight and efficient HTML fetching and parsing without the overhead of headless browsers.

These choices ensure that **Page Pulse** remains responsive, resource-efficient, and production-ready while supporting future growth.
